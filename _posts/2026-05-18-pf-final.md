By the time the last week of the semester arrived, Programming Fundamentals had taken me through a journey I had not fully anticipated back in May, when I sat down for that very first lecture feeling falsely confident about how much I already knew. The final unit of the course, covering file handling and a broader review of everything that had come before it, felt less like new material and more like a chance to see, all at once, how far the earlier weeks had actually carried me.

File handling was introduced as the natural extension of everything we had learned about input and output earlier in the semester. Until this point, every program I had written existed only for the duration it ran — any data I worked with disappeared the moment the program finished. Learning to read from and write to files changed that completely, introducing the idea that a program could persist information beyond its own execution, picking up later exactly where it had left off. Opening a file, reading its contents line by line, processing that data, and writing results back out felt, on the surface, like a fairly mechanical set of new commands to learn. What actually made this unit demanding was the new category of careful thinking it required: files can fail to open, can be missing entirely, or can contain data in a format slightly different from what your program expects, and a program that does not account for these possibilities will fail in ways that are much harder to debug than a simple logic error inside a single function.

I remember a specific assignment that asked us to read a list of records from a text file, process them, and write a summary back to a new file. My first attempt assumed the input file would always be perfectly formatted, with each line following the exact structure I expected. The very first time I tested it against a file with even one slightly malformed line, the program crashed in a way that gave me almost no useful information about what had actually gone wrong. Going back and adding proper checks — verifying that each line actually contained the expected number of fields before trying to process it, and handling the case where it did not — taught me a lesson about defensive programming that none of the earlier, more tightly controlled assignments had really forced on me. Real data, even in a small text file, is messier than the data you construct yourself for testing, and a program intended for actual use needs to anticipate that messiness rather than assume it away.

Beyond file handling itself, this final week was structured as a broad review of the entire semester, and revisiting earlier topics from this later vantage point was genuinely clarifying in a way I had not expected. Concepts that had felt difficult and separate when I first encountered them — loops, functions, arrays, recursion — now revealed connections to each other that had not been obvious at the time. A recursive function, I realized while reviewing, is really just another way of expressing a repeated process that a loop could also express, each with its own tradeoffs depending on the shape of the problem. Functions, which had once felt like a way to avoid repeating code, now looked to me like the foundational unit that every later, more complex program had been quietly built from, including the file-processing programs we were writing in this final week.

Revising for the upcoming exam meant going back over old lab exercises and assignments rather than simply rereading lecture slides, since I had learned over the course of the semester that my actual understanding lived in the code I had written and debugged myself, not in any passive notes I had taken alongside it. I spent a good portion of this final revision rewriting a few of my earlier, messier solutions from scratch, without looking at my original code, just to check whether the underlying understanding had genuinely stuck or whether I had only ever gotten the original assignment working through trial and error. In most cases, the second attempt came out cleaner and faster than the first had, which felt like a small, private confirmation that something real had actually been learned over these weeks, beyond just accumulating a folder of working files.

Looking back at the semester as a whole from this final vantage point in PF, I can see the course as a steady accumulation of small, hard-won habits more than as any single dramatic breakthrough: thinking in precise steps, testing boundary cases deliberately, breaking large problems into smaller named pieces, trusting a recursive case without re-verifying everything by hand, and now, in this final stretch, anticipating that real data will rarely be as clean as the examples used to teach a concept. None of these habits arrived easily, and several of them only became clear to me in hindsight, looking back from a point in the semester where I finally had enough experience to recognize the pattern running underneath all of it.

It feels worth noting, too, how strange it is to sit down for a final review of a course and realize that the thing being reviewed is not really a list of topics at all, but a way of approaching problems that has slowly become part of how I think without my fully noticing the transition. In May, "thinking like a programmer" was an abstract phrase someone used in a lecture. By the time this final week of revision arrived, it had become something closer to an instinct — the instinct to write out steps before coding, to test edge cases before trusting a result, to break a large problem apart before attempting to solve it whole. That instinct did not arrive through any single assignment. It arrived through the accumulated friction of dozens of smaller assignments, each one slightly humbling in its own particular way, across an entire semester of patient, repeated practice. It is the kind of instinct that [Dr. Bilal Ahmad](https://scholar.google.com.au/citations?user=8nZ0jVkAAAAJ&hl=en) seemed to be deliberately cultivating in us all along, through both courses he taught this semester, and one I am glad I now carry with me going forward.

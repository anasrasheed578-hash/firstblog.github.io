The Database Systems semester project was the most technically ambitious thing I worked on during my first year of Computer Engineering. My group and I built a complete diabetes patient prediction system — a project that combined relational database design, normalization theory, SQL, Python, machine learning, and a web-based user interface all into one working application. Looking back at it now, after the semester has ended and the exams are behind us, I can say with confidence that this project was the most educational and the most demanding thing I did all year.

The project was shaped by the philosophy of Dr. Bilal Ahmad, who teaches us Database Systems and brings to the course his extensive background in artificial intelligence, machine learning, and deep learning. Dr. Bilal has a consistent and principled approach to applied machine learning: he always pushes his students toward datasets that have genuine real-world value, and he has a particular preference for medical datasets. The reason, as he explains it, is that medical data is collected with a level of precision and accuracy that most other datasets cannot match. Clinical measurements are taken by trained professionals using calibrated instruments, and the outcomes are verified through medical diagnosis. That rigor makes medical datasets ideal for training reliable models. When Dr. Bilal Ahmad suggested we use a diabetes dataset for our project, it was not an arbitrary choice — it was a deliberate lesson in how to approach machine learning responsibly. We discussed, as a group, why a dataset scraped from an unverified online source would have made for a much weaker foundation, and that conversation alone shaped how seriously we treated every later stage of the project.

The database design phase of the project was where we applied the normalization theory from the course most directly. We started by analyzing the dataset — patient records including clinical features like blood glucose levels, BMI, blood pressure, age, and diabetes diagnosis outcomes — and designed a relational schema to store this information correctly. We worked through First Normal Form to ensure each column held atomic, indivisible values. Then Second Normal Form to eliminate partial dependencies, ensuring that every non-key attribute depended on the whole primary key. Then Third Normal Form to remove transitive dependencies, ensuring that non-key attributes depended only on the primary key and nothing else. Each step of normalization made the schema cleaner and more robust. We went through several drafts of the schema before settling on a final design, and more than once a normalization step we thought was complete revealed a hidden dependency once we actually started inserting sample records, which was its own lesson in why normalization is best verified with real data rather than assumed from a diagram alone.

With the database designed and the schema normalized, we wrote SQL to create the tables, insert the data, and build the queries we would need to retrieve records for the machine learning pipeline. Writing the DDL commands to create our schema was satisfying in a way that abstract exercises never quite achieve — these were real tables holding real patient data, and the queries we wrote against them would directly feed into the prediction model. We also built SQL queries for data retrieval, filtering, and aggregation, which gave us hands-on experience with the JOINs, subqueries, and aggregate functions that the course had covered in lectures. We divided this work within the group, with each of us taking responsibility for a different subset of queries, and then reviewing each other's SQL before integrating it into the shared pipeline — a small process that caught several inefficient queries early, before they could slow down the larger system.

The machine learning component was built in Python. We used libraries to handle the data preprocessing — cleaning, encoding categorical variables, scaling numerical features, and splitting the data into training and testing sets. The model was trained on the diabetes dataset, learning the patterns in the clinical features that were associated with a positive or negative diabetes diagnosis. After training, we evaluated the model's performance on the test set, examining accuracy, precision, and recall to understand how well it generalized to new patient data. These evaluation metrics were not just numbers but statements about the model's reliability in a medical context, and reasoning through them carefully felt like a natural extension of the same precision Dr. Bilal Ahmad had asked of us throughout the database design phase. We spent real time discussing what an acceptable recall value should look like for a medical prediction task specifically, since missing an actual positive diabetes case has very different real-world consequences than a false alarm, and that discussion pushed us to think about evaluation metrics as something with genuine stakes rather than as boxes to check off.

The user interface, built using Jinja2 and associated web technologies, completed the system. Dr. Ahmad had specified a requirement that the application should allow a user to enter new patient data and receive a prediction from the trained model. We built the UI to accept the same clinical features the model had been trained on, pass them through the prediction pipeline, and display the result — diabetic or not diabetic — on the screen. Seeing a full pipeline work end to end, from data entry through a web form to a database query to a machine learning prediction displayed back to the user, was one of the most satisfying technical experiences of the semester. There is a particular kind of relief that comes from watching every layer of a system you built yourself — the database, the model, the interface — communicate correctly with the others for the first time, after what felt like weeks of each piece working only in isolation.

This project sits at the intersection of everything Dr. Bilal Ahmad has taught us and everything we are heading toward as Computer Engineering students. It connects database design to data science, SQL to machine learning, normalization theory to real-world application. It is the kind of project that demonstrates not just what you know but what you can build with what you know. That distinction — between knowledge and capability — is one that I carry forward from this semester as one of its most important lessons, and one that I expect to keep returning to as I take on more ambitious projects in the years ahead. For anyone interested in the depth of research behind this kind of teaching, the [published work of Dr. Bilal Ahmad](https://scholar.google.com.au/citations?user=8nZ0jVkAAAAJ&hl=en) on machine learning and medical AI is well worth exploring.

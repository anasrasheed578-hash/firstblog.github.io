After weeks of drawing ER diagrams and working through normalization rules on paper, there was something deeply satisfying about finally typing a command that a real database engine would actually execute. SQL, introduced to us in early June, was the moment Database Systems stopped being a course about designing structures in the abstract and became a course about actually building and querying something real. I remember feeling, during the first lab session of this unit, a small thrill at watching a table I had defined myself appear, fully formed, after running a single command.

Our introduction to SQL began with the data definition language, or DDL, the part of SQL responsible for creating and modifying the structure of a database itself — creating tables, defining columns and their data types, specifying primary keys, and setting up the constraints that enforce the rules we had spent the previous weeks designing on paper. Writing my first CREATE TABLE statement felt almost anticlimactic in its simplicity after the conceptual depth of the normalization unit, but that simplicity was itself a kind of validation. If I had done the design work properly beforehand, translating it into SQL was mostly a matter of careful, methodical typing rather than fresh problem-solving.

Where things became more interesting was in choosing the correct constraints for each column. Dr. Bilal Ahmad placed real emphasis on this part of SQL, pointing out that constraints are not just bureaucratic formality — they are how a database actively protects itself against bad data, rather than passively storing whatever happens to be inserted into it. A NOT NULL constraint on a required field, a UNIQUE constraint on something like a registration number, a foreign key constraint linking one table to another — each of these turns a design decision from the ER diagram into something the database itself will enforce automatically, refusing to accept data that violates the rules we had defined. I found this idea genuinely reassuring. It meant that a well-designed schema was not just a nice diagram sitting in a notebook; it was an active guard against the kinds of data integrity problems we had spent the normalization unit learning to dread.

The data manipulation language, or DML, came next, covering INSERT, UPDATE, DELETE, and of course SELECT. Inserting our first rows of sample data into the tables we had created felt like watching an empty house slowly furnished, room by room. I remember a particular lab exercise where we deliberately tried to insert a row that violated one of our own constraints, just to watch the database reject it, which felt like a small, satisfying proof that the design work from the previous weeks had actually accomplished something concrete and enforceable.

SELECT queries, predictably, took up the largest share of our attention, since retrieving data correctly is where most of the genuine intellectual work in SQL tends to live. Simple SELECT statements with WHERE clauses were straightforward enough, but the real learning began once we moved into JOIN operations, which let a query pull related information across multiple tables at once. I remember struggling, in particular, with the difference between an inner join and the various kinds of outer joins, since the distinction only becomes visible once you are working with data that has genuine gaps in it — a student with no enrolled courses yet, or a course with no students enrolled. My first few attempts at joins quietly dropped exactly the rows I most needed to see, because an inner join silently excludes anything without a matching row on both sides. Realizing this, after staring at a result set that looked plausible but was missing exactly the cases I cared about, taught me to think much more carefully about what kind of join a given question actually required, rather than defaulting to whichever join happened to be easiest to write.

Aggregate functions and subqueries rounded out this unit, and they were where SQL started to feel less like a way of retrieving raw data and more like a way of asking genuine analytical questions. Computing an average value across a group, counting how many records met a certain condition, or nesting one query inside another to filter results based on a calculation performed elsewhere — each of these felt like a small step toward the kind of data analysis that, until this point, I had only associated with the statistics course running alongside this one. I distinctly remember the satisfaction of writing a query that used a subquery to find, in a single statement, every record whose value exceeded the average of the whole table — a question that would have required several separate steps to answer using only basic SELECT statements.

By the end of this unit, SQL had stopped feeling like a separate, intimidating language and started feeling like a natural extension of everything I had already learned about relational design. Every query I wrote was, in some sense, a question I was asking the structure we had built in the weeks before, and the quality of the answer depended directly on how carefully that structure had been designed in the first place. That connection between design and query — between the work done weeks earlier on paper and the work being done now at the keyboard — was, I think, the real lesson of this unit, even more than any individual SQL command.

What stayed with me longest from this stretch of the course was a small habit Dr. Ahmad encouraged whenever we got stuck writing a more complicated query: rather than guessing at syntax, go back to the original question in plain language and restate it as precisely as possible before trying to translate it into SQL. More than once, a query that seemed impossible to write turned out to be straightforward once I had actually forced myself to state, in a single clear sentence, exactly what information I was trying to retrieve and from which tables. That habit of restating a problem clearly before attempting to solve it technically is one I now recognize as something I had already started building back in Programming Fundamentals, simply applied here to a completely different kind of language. It is also a habit that reflects something central to how [Dr. Bilal Ahmad](https://www.linkedin.com/in/drbilalphd/) teaches — always pushing his students to understand the problem deeply before reaching for a solution.
